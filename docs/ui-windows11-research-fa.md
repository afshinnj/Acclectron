# تحقیق و نقشهٔ راه بازطراحی رابط کاربری Acclectron با سبک Windows 11

**وضعیت:** تحقیق طراحی و ممیزی فنی رابط کاربری

**مخزن بررسی‌شده:** `afshinnj/Acclectron`

## نتیجهٔ اجرایی

بله، شکل ظاهری Acclectron را می‌توان به‌صورت قابل‌توجهی به برنامه‌های Windows 11 نزدیک کرد، بدون آن‌که Electron، ساختار دیتابیس یا منطق حسابداری بازنویسی شود. پروژهٔ فعلی از چند پایهٔ مناسب برخوردار است: پوستهٔ دسکتاپی، نوار فعالیت، نوار کناری، تم روشن و تاریک، پنل‌های کارت‌مانند، پنجره‌های modal و پشتیبانی از رابط راست‌به‌چپ. بااین‌حال، ظاهر فعلی هنوز یک Design System یکپارچه ندارد. رنگ‌ها، فاصله‌ها، شعاع گوشه‌ها و اندازهٔ متن در بخش‌های مختلف به‌صورت پراکنده تعریف شده‌اند. به همین دلیل محصول بیشتر شبیه یک داشبورد سفارشی تاریک است تا یک برنامهٔ منسجم با زبان بصری Windows 11.

پیشنهاد اصلی این است که بازطراحی در چهار لایه انجام شود: نخست توکن‌های بصری و پوستهٔ اصلی، سپس ناوبری و ساختار صفحات، بعد کنترل‌های فرم و جدول، و در پایان دسترس‌پذیری و آزمون دیداری. این مسیر کم‌ریسک‌تر از بازنویسی کامل `renderer.js` است و امکان حفظ قابلیت‌های فعلی را فراهم می‌کند.

## مبنای طراحی Windows 11 و Fluent

مایکروسافت Fluent را بر تجربه‌ای طبیعی، متمرکز، فراگیر و قابل‌شناسایی بنا می‌کند. در راهنمای Fluent، کاهش شلوغی بصری برای حفظ تمرکز کاربر یک اصل صریح است. همچنین، طراحی باید با الگوهای آشنای پلتفرم هماهنگ باشد و بخش زیادی از رفتارها بر اساس کنترل‌ها و الگوهای شناخته‌شدهٔ سیستم شکل بگیرد [1]. راهنمای رسمی Windows نیز طراحی را به چند حوزهٔ مستقل مانند layout، navigation، typography، color، motion و accessibility تقسیم می‌کند [2].

برای Acclectron این اصول به معنای حذف کارت‌ها یا رنگ‌های فعلی نیست؛ بلکه به معنای کاهش تنوع بی‌دلیل، ایجاد سلسله‌مراتب روشن و استفادهٔ محدودتر از accent color است. رنگ تأکیدی باید برای اقدام اصلی، وضعیت انتخاب‌شده و هشدارهای مهم استفاده شود، نه برای تزئین همهٔ عناصر [5].

## ممیزی وضعیت فعلی پروژه

رابط کاربری در `renderer.js` به‌صورت runtime ساخته می‌شود و `index.html` نسبتاً کوچک است. این معماری برای ادامهٔ کار مناسب است، اما باعث شده بخش بزرگی از markup و رفتار UI در یک فایل بزرگ متمرکز شود. اندازهٔ فایل‌های اصلی رابط به‌صورت زیر است:

| بخش | وضعیت فعلی |
| --- | ---: |
| `renderer.js` | ۳٬۷۶۸ خط |
| `styles.css` | ۱٬۰۲۳ خط |
| `main.js` | ۵۷۶ خط |
| `preload.js` | ۱۵۹ خط |
| فرم‌ها | ۲۲ مورد |
| عناصر button یا ارجاع‌های button | حدود ۲۰۷ مورد |
| عناصر input یا ارجاع‌های input | حدود ۱۶۹ مورد |
| `aria-label` | ۱۰ مورد |
| `title` | ۱۳ مورد |

وجود تنها ۱۰ `aria-label` در برابر تعداد زیاد کنترل‌های تعاملی نشان می‌دهد که دسترس‌پذیری باید بخشی از بازطراحی باشد، نه مرحله‌ای فرعی. این عدد به‌تنهایی ثابت نمی‌کند همهٔ کنترل‌ها مشکل دارند، اما نشان می‌دهد پوشش نام‌گذاری دسترس‌پذیر محدود است.

در CSS رنگ‌های hex به‌صورت مستقیم در تعداد زیادی از قواعد تکرار شده‌اند. شعاع گوشه‌ها نیز از ۴، ۵، ۶، ۷، ۸، ۹، ۱۰، ۱۱، ۱۲ و ۱۸ پیکسل استفاده می‌کند. این پراکندگی، هماهنگ‌کردن تم روشن و تاریک و اصلاح یکپارچهٔ ظاهر را دشوار می‌کند. برای مقایسه، راهنمای Windows سه سطح اصلی را پیشنهاد می‌کند: شعاع ۴ پیکسل برای کنترل‌های درون صفحه و شعاع ۸ پیکسل برای پنجره‌ها، flyoutها و overlayها [6].

بخش قابل‌توجهی از متن‌ها با اندازهٔ ۹ تا ۱۲ پیکسل تعریف شده‌اند. راهنمای تایپوگرافی Windows برای متن عادی مقدار ۱۴ پیکسل و برای caption مقدار ۱۲ پیکسل را در type ramp خود قرار می‌دهد و استفاده از وزن Semibold را برای عنوان‌ها پیشنهاد می‌کند [7]. بنابراین، بسیاری از متن‌های فعلی برای سبک Windows 11 کوچک‌تر از مقدار مناسب هستند؛ به‌خصوص در جدول‌ها، برچسب‌های فرم و اطلاعات ثانویه.

## مقایسهٔ وضعیت فعلی با هدف Windows 11

| حوزه | وضعیت فعلی | هدف پیشنهادی |
| --- | --- | --- |
| ساختار کلی | activity bar، sidebar و محتوای RTL | NavigationView-like shell با یک مسیر اصلی روشن |
| ناوبری | تعداد زیادی مقصد در سطح‌های نزدیک | گروه‌بندی مقصدها و کاهش تصمیم‌گیری هم‌زمان |
| رنگ | رنگ‌های hex متعدد و کنتراست‌های محلی | توکن‌های semantic برای سطح، متن، border، accent و status |
| گوشه‌ها | تنوع زیاد از ۴ تا ۱۸ پیکسل | ۴ پیکسل برای کنترل‌ها و ۸ پیکسل برای overlay و container |
| متن | اندازه‌های متعدد، شامل ۹ تا ۱۲ پیکسل | body حدود ۱۴، caption حدود ۱۲، عنوان ۲۰ تا ۲۸ پیکسل |
| فرم‌ها | کنترل‌های سفارشی با قواعد پراکنده | ارتفاع و فاصلهٔ ثابت، focus ring مشترک و وضعیت خطای یکسان |
| جدول‌ها | داده‌محور و فشرده | header ثابت، ردیف قابل اسکن، hover و selection واضح |
| modalها | چند الگوی متفاوت | یک الگوی dialog با سطح، سایه و فاصلهٔ یکسان |
| تم | light و dark موجود | light/dark مبتنی بر همان توکن‌ها و قابل بررسی با accentهای مختلف |
| RTL | پشتیبانی عملیاتی موجود | تعریف صریح direction، alignment و فونت فارسی در سطح design token |
| دسترس‌پذیری | پوشش محدود ARIA و focus نامشخص | keyboard navigation، focus قابل مشاهده، label و status غیررنگی |

## معماری بصری پیشنهادی

### ۱. توکن‌های مرکزی

پیش از اصلاح تک‌تک صفحات، یک لایهٔ توکن در ابتدای `styles.css` تعریف شود. این توکن‌ها باید رنگ، سطح، متن، فاصله، ارتفاع کنترل، شعاع و سایه را پوشش دهند. نمونهٔ پیشنهادی زیر برای آغاز کار است و باید با اسکرین‌شات واقعی و آزمون کنتراست نهایی شود:

```css
:root {
  --win-bg: #f7f7f8;
  --win-surface: #ffffff;
  --win-surface-subtle: #f3f3f3;
  --win-text: #1f1f1f;
  --win-text-secondary: #5f5f5f;
  --win-border: #d6d6d6;
  --win-accent: #0067c0;
  --win-danger: #c42b1c;
  --win-success: #107c10;
  --win-radius-control: 4px;
  --win-radius-overlay: 8px;
  --win-space-1: 4px;
  --win-space-2: 8px;
  --win-space-3: 12px;
  --win-space-4: 16px;
  --win-space-5: 24px;
}

:root[data-theme="dark"] {
  --win-bg: #202020;
  --win-surface: #2b2b2b;
  --win-surface-subtle: #333333;
  --win-text: #ffffff;
  --win-text-secondary: #c8c8c8;
  --win-border: #454545;
  --win-accent: #60cdff;
}
```

Fluent از یک مقیاس فاصلهٔ چهارپیکسلی استفاده می‌کند و نمونه‌های آن از ۴، ۸، ۱۲، ۱۶، ۲۰، ۲۴ و مقادیر بالاتر تشکیل می‌شوند [3]. استفاده از همین ramp در Acclectron باعث می‌شود header، فرم، جدول و کارت‌ها ریتم مشترک داشته باشند.

### ۲. پوستهٔ برنامه

ساختار فعلی activity bar و sidebar را می‌توان حفظ کرد، اما باید نقش هرکدام روشن شود. activity bar فقط باید مقصدهای اصلی و کم‌تعداد را نشان دهد. sidebar باید نام مقصدها و گروه‌ها را نمایش دهد. بخش محتوایی باید یک page header ثابت داشته باشد که شامل عنوان، توضیح کوتاه و commandهای اصلی باشد.

راهنمای ناوبری Windows بر سه ویژگی تأکید می‌کند: ثبات، سادگی و وضوح. همچنین، برای ناوبری سطح بالا بیش از پنج مقصد، ناوبری عمودی مناسب است؛ اما نباید کاربر با گزینه‌های زیاد در یک سطح روبه‌رو شود [4]. در Acclectron، فروش، خرید، کالاها، اشخاص، گزارش‌ها و تنظیمات می‌توانند گروه‌های اصلی باشند و عملیات جزئی‌تر درون هر گروه قرار گیرند.

### ۳. داشبورد

داشبورد فعلی باید از یک صفحهٔ کارت‌محور به یک صفحهٔ تصمیم‌محور تبدیل شود. بالای صفحه بهتر است چهار شاخص اصلی قرار بگیرد: فروش امروز، فروش دوره، سود ناخالص و موجودی هشدار. بعد از آن، نمودار روند فروش و فهرست عملیات یا هشدارهای مهم قرار گیرد. هر کارت باید فقط یک پیام اصلی داشته باشد و با رنگ accent اشباع نشود.

برای گزارش‌های فروش، نمودار باید legend قابل‌فهم، tooltip خوانا، برچسب تاریخ شمسی و خلاصهٔ متنی داشته باشد. اطلاعات مهم نباید فقط از طریق رنگ یا نمودار منتقل شوند؛ مقدار عددی و وضعیت متنی نیز باید کنار آن قرار گیرد.

### ۴. فرم‌ها و کنترل‌ها

تمام inputها، selectها و buttonها باید ارتفاع و focus ring مشترک داشته باشند. پیشنهاد عملی برای نسخهٔ دسکتاپ این است که ارتفاع کنترل‌ها حدود ۳۶ تا ۴۰ پیکسل باشد و فاصلهٔ label تا کنترل و فاصلهٔ بین گروه‌ها از ramp چهارپیکسلی پیروی کند. کنترل اصلی هر فرم باید با یک primary action مشخص شود و buttonهای ثانویه از نظر شدت بصری پایین‌تر باشند.

برای فرم‌های فارسی، label باید همیشه قابل مشاهده باشد و placeholder فقط نقش نمونه داشته باشد. خطای فرم باید در کنار کنترل مرتبط نمایش داده شود، نه فقط در toast عمومی. فرم‌های طولانی تنظیمات بهتر است به بخش‌های واضح با tab یا navigation داخلی تقسیم شوند.

### ۵. جدول‌ها و داده‌های حسابداری

جدول‌های Acclectron بخش اصلی تجربهٔ کاربر هستند. پیشنهاد می‌شود header جدول sticky باشد، ردیف انتخاب‌شده پس‌زمینهٔ مشخص داشته باشد، اعداد مالی با alignment ثابت نمایش داده شوند و وضعیت‌هایی مانند پرداخت‌شده، معوق، کمبود موجودی و لغوشده علاوه بر رنگ، متن یا آیکون داشته باشند. برای ستون‌های کم‌اهمیت می‌توان در عرض‌های کوچک‌تر اولویت نمایش تعریف کرد.

## دسترس‌پذیری و کیفیت ادراکی

راهنمای Microsoft برای متن، حداقل نسبت کنتراست ۴٫۵:۱ را برای متن قابل‌مشاهده در تجربهٔ عادی پیشنهاد می‌کند و تأکید دارد که high-contrast نباید راه‌حل اصلی متن کم‌خوانا باشد [8]. در نتیجه، تم روشن Acclectron باید با ابزار کنتراست آزمایش شود و رنگ‌های وضعیت نباید تنها عامل تشخیص باشند.

متن استاتیک نباید داخل کنترل focusable قرار گیرد و هر کنترل قابل‌ویرایش باید نقش و label درست داشته باشد [8]. برای Acclectron، حداقل اقدامات شامل اضافه‌کردن label واقعی به تمام inputها، تعریف `aria-label` برای buttonهای icon-only، تعیین ترتیب منطقی Tab، نمایش focus واضح و بررسی صفحه‌ها با Narrator است.

راهنمای typography همچنین توصیه می‌کند متن در برابر افزایش مقیاس خوانا بماند و طراحی به‌صورت گسترده text scaling را غیرفعال نکند [8]. در Electron باید این موضوع با تغییر zoom یا اندازهٔ فونت و بررسی شکست layout آزمایش شود.

## نقشهٔ راه اجرایی

### مرحلهٔ اول: یکپارچه‌سازی پایه

در این مرحله فقط CSS و markupهای مشترک اصلاح می‌شوند. توکن‌های رنگ، فاصله، شعاع، سایه و typography ایجاد می‌شوند. رنگ‌های مستقیم در قواعد عمومی به توکن تبدیل می‌شوند. سپس تم روشن و تاریک با همان semantic tokenها بازنویسی می‌شوند.

**خروجی:** ظاهر پایهٔ یکنواخت، کاهش پراکندگی CSS و امکان تغییر سریع theme.

### مرحلهٔ دوم: پوسته و ناوبری

در این مرحله activity bar، sidebar، page header و حالت collapsed بازطراحی می‌شوند. مقصدها گروه‌بندی می‌شوند، active state واضح‌تر می‌شود و عنوان صفحه همیشه قابل تشخیص خواهد بود. این مرحله بیشترین اثر را بر حس Windows 11 دارد.

**خروجی:** shell یکپارچه با NavigationView-like behavior و کاهش شلوغی دیداری.

### مرحلهٔ سوم: کنترل‌ها، فرم‌ها و جدول‌ها

Button، input، select، checkbox، modal، table و toast به component styleهای مشترک منتقل می‌شوند. در این مرحله height، padding، radius، focus و disabled state یکسان می‌شوند.

**خروجی:** فرم‌های قابل اسکن‌تر و کاهش تفاوت ظاهری میان صفحات.

### مرحلهٔ چهارم: داشبورد و گزارش‌ها

کارت‌های شاخص، نمودارها، جدول خلاصه و پنل پیش‌بینی بر اساس سلسله‌مراتب جدید بازچینش می‌شوند. رنگ accent فقط برای انتخاب، اقدام اصلی و نکات کلیدی باقی می‌ماند.

**خروجی:** داشبوردی که به جای نمایش حجم زیادی از اطلاعات، تصمیم‌های مهم روزانه را برجسته می‌کند.

### مرحلهٔ پنجم: accessibility و آزمون دیداری

در پایان، تمام صفحات در تم روشن و تاریک، اندازهٔ پنجرهٔ معمولی، صفحهٔ بزرگ، مقیاس متن بزرگ‌تر و navigation با کیبورد بررسی می‌شوند. تست‌های smoke برنامه و تست‌های فعلی منطق نیز باید بدون تغییر رفتار تجاری اجرا شوند.

**خروجی:** UI قابل اتکا برای استفادهٔ روزمره و انتشار نسخهٔ جدید.

## ریسک‌ها و محدودیت‌ها

Acclectron یک برنامهٔ Electron است، نه WinUI 3. بنابراین می‌توان ظاهر، spacing، رنگ، typography، navigation و رفتارهای مشابه را ساخت، اما تمام جزئیات native مانند Acrylic واقعی، Mica، system backdrop و برخی رفتارهای accessibility به‌صورت کامل و بدون native integration تضمین نمی‌شوند. استفادهٔ افراطی از blur یا شفافیت نیز برای برنامهٔ حسابداری توصیه نمی‌شود، چون خوانایی جدول‌ها و گزارش‌ها را کاهش می‌دهد.

همچنین، شبیه‌سازی بیش از حد Windows 11 نباید به قیمت کاهش سرعت کار کاربران حرفه‌ای تمام شود. کاربران حسابداری با keyboard، tab، ورود سریع عدد و جدول متراکم کار می‌کنند. ظاهر جدید باید از این workflowها پشتیبانی کند، نه آن‌که صرفاً فضای خالی و کارت‌های بزرگ اضافه کند.

## پیشنهاد نهایی

بازطراحی Windows 11 برای Acclectron **عملی و کم‌ریسک است**، به شرط آن‌که به‌صورت design-system refactor انجام شود و نه مجموعه‌ای از اصلاحات جداگانه در صفحات. اولویت پیشنهادی عبارت است از: توکن‌های مرکزی، پوسته و ناوبری، کنترل‌ها و جدول‌ها، سپس داشبورد و در پایان دسترس‌پذیری. با این ترتیب، می‌توان بدون تغییر منطق فروش و حسابداری، محصول را از نظر ظاهر به زبان بصری Fluent نزدیک کرد و هم‌زمان خوانایی و بهره‌وری آن را افزایش داد.
